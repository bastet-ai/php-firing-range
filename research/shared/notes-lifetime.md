# Notes: lifetimes — what outlives what in the progress machinery

[GLM] 2026-10-21T03:22:40Z — refs php-src-83 unless marked 74.

## Request-phase ordering (critical context)
- `php_request_startup`: ... zend_activate(); sapi_activate(); ... **php_hash_environment(); zend_activate_modules();** — main/main.c:1833-1834. So the ENTIRE multipart parse (and all progress callbacks) runs **before any module RINIT**, including session's. Session RINIT would call php_rinit_session(auto_start) at session.c:2815-2818.
- Consequence 1: during progress callbacks, PS globals hold **values stale from the previous request (NTS)** except what progress itself initializes. `php_rinit_session(0)` is called by FILE_START (session.c:3122) — this is the code's own workaround for running pre-RINIT: resolves PS(mod) + PS(serializer) from INI (session.c:2779-2813).
- Consequence 2: my earlier auto_start+fd-leak/deadlock hypothesis is DEAD WRONG — at parse time auto_start has not run, so there is no pre-open session fd to lose. Corrected here for the record. (If a second treat_data ran post-RINIT it could matter — it doesn't; rfc1867_post_handler runs once, at hash_environment.)

## Progress struct lifecycle (php_session.h:122-139)
- Alloc: MULTIPART_EVENT_START ecalloc (session.c:3115). Store: PS(rfc1867_progress) (php_session.h:190).
- Freed ONLY at MULTIPART_EVENT_END (session.c:3262-3268): dtor(data), dtor(sid), smart_str_free(key), efree, PS(rfc1867_progress)=NULL.
- **PS(rfc1867_progress) is NOT in php_rinit_session_globals (session.c:108-122) nor php_rshutdown_session_globals (session.c:136-160) reset lists.** ⇒ On zend_bailout mid-parse (fatal during update — e.g., memory_limit in a user save handler), EVENT_END never fires; struct + zvals leak to arena reclamation; the stale PS(rfc1867_progress) survives into the next request. Next multipart request EVENT_START (session.c:3111-3119) overwrites the pointer BEFORE any dereference (START is the first event; no case dereferences the old pointer). Checked both branches: **no UAF found via stale rfc1867_progress** — log as "checked, benign; leak only".
- The request arena (Zend MM request heap) is destroyed at request shutdown, so leaked emalloc'd progress data dies with the request; PS globals themselves are not arena memory (ZEND_MODULE_GLOBALS) and persist across requests in NTS.

## Session lifecycle driven mid-request by progress
- Every `php_session_rfc1867_update` (session.c:3052-3083) runs: php_session_initialize() → { s_open; sid create-or-validate(use_strict_mode only); php_session_reset_id() (session.c:456+); php_session_track_init() (session.c:228-246 — deletes $GLOBALS['_SESSION'], dtors http_session_vars, fresh array, rebinds both); s_read; **php_session_gc(0)** (session.c:475); php_session_decode(val) } → cancel-check → insert progress->data (Z_TRY_ADDREF, zend_hash_update session.c:3080-3081) → php_session_flush(1) (session.c:1687-1697) → encode → s_write/s_update_timestamp → **s_close** (php_session_save_current_state session.c:555-558). So each update = full open→read→GC→decode→encode→write→close cycle, attacker-paced via freq/min_freq (INI defaults freq=1%, min_freq=1s; slow-loris uploads can hold a session open/write-looping for minutes).
- **initialize() FAILURE IS IGNORED by update/cleanup** (no return check at session.c:3073, 3088): on s_open/s_read failure the code still sets `PS(session_status) = php_session_active` (session.c:3074, 3089) and proceeds to insert into whatever $_SESSION exists (track_init ran if failure was at s_read) → flush "writes" (mod_data NULL → skipped) → status left ACTIVE with broken storage. Confirmed by expected output of tests/rfc1867_sid_invalid.phpt (invalid sid `_` → warnings, yet $_SESSION data present in script, session_start() no-op). This is state corruption by design — worth flagging for hardening.
- GC amplification: php_session_gc(0) samples gc_probability/gc_divisor (default 1/100) on EVERY initialize — progress multiplies initialize count per request (every 1% of body, ≥1s apart). files GC = opendir+unlink of expired files under save_path (mod_files.c). Not a corruption vector; amplification/DoS note.
- EVENT_END teardown order (session.c:3259-3270): cleanup-or-final-update INSIDE `if (sid && key)`; then php_rshutdown_session_globals() (session.c:3261) — only when sid&&key present. If the POST had no PHP_SESSION_UPLOAD_PROGRESS field and no sid, session teardown at EVENT_END is SKIPPED entirely and the normal module RSHUTDOWN handles state (session.c:2829-2839: flush-if-active + rshutdown — double-rshutdown is idempotent: all fields already NULL/undef).

## Aliasing (cached zval pointers) — checked, stable within a request
- `progress->post_bytes_processed` → element of Z_ARRVAL(progress->data), cached at first FILE_START (session.c:3151); `current_file_bytes_processed` → element of current_file, re-cached per FILE_START (session.c:3163). Writes at FILE_DATA (session.c:3222-3226) and FILE_END (session.c:3255).
- data array: elements added only at first FILE_START, BEFORE caching; FILE_END's add_assoc_* all hit existing keys (in-place) ⇒ no rehash after caching ⇒ pointers stable. EVENT_END non-cleanup branch SEPARATE_ARRAY(&progress->data) (session.c:3248) dup semantics: post_bytes_processed then writes into the ORIGINAL (owned by $_SESSION) — harmless-but-wrong-target write, not UAF (original alive until the subsequent zend_hash_update replaces it).
- Ownership of progress->files/current_file/data: `add_*_zval*` are ownership-transfer (no addref): add_assoc_zval_ex → zend_symtable_str_update (Zend/zend_API.c:1916-1919), add_next_index_zval → zend_hash_next_index_insert (Zend/zend_API.h:621-625, zend_hash.c:1226-1229), hash update copies zval without addref (Zend/zend_hash.c _zend_hash_add_or_update_i). ONLY the $_SESSION insert does explicit Z_TRY_ADDREF (session.c:3080). Re-verified refcount flow across multi-file POSTs and EVENT_END separation: consistent, no leak/UAF found in 83 or 74 (identical logic; 74 session.c:3213-3229).

## Cross-request staleness of PS(mod) etc. (NTS)
- At EVENT_END with sid&&key but NO file parts (pure form-field POST + PHP_SESSION_UPLOAD_PROGRESS), php_session_rfc1867_cleanup → php_session_initialize runs with **PS(mod) resolved by the PREVIOUS request's php_rinit_session** (or NULL on first request). ps_module structs are static/persistent → valid pointers. mod_user: mod_user_implemented can be stale TRUE from previous request while mod_user_names zvals were FREED by RSHUTDOWN (SESSION_FREE_USER_HANDLER session.c:2837-2850) — they are ZVAL_UNDEF, and ps_call_handler guards undefined callbacks (mod_user.c) → warning path, no dangling zval use found. Log as "checked, benign-by-construction".
