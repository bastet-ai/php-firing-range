The progress struct is request-heap allocated at START and freed only at multipart END (`src/php-src-83/ext/session/session.c:3113-3118,3264-3271`). RFC1867 calls END before freeing parser buffers (`src/php-src-83/main/rfc1867.c:1258-1274`), while callback copies the form marker, SID, field name, filename, and temp filename, so parser-owned strings do not outlive their owners (`src/php-src-83/ext/session/session.c:3140-3146,3195-3200,3235-3237`).

Highest-interest memory-safety hypothesis: `progress->post_bytes_processed` and `current_file_bytes_processed` are raw pointers into nested HashTable buckets (`src/php-src-83/ext/session/php_session.h:134-138`), set at `src/php-src-83/ext/session/session.c:3183,3207-3209` and written later at `src/php-src-83/ext/session/session.c:3222-3223,3242`. Normal updates addref the top array before inserting it into session state and session flush leaves the progress-owned reference alive (`src/php-src-83/ext/session/session.c:3073-3083`), so ordinary serialize/close does not invalidate them. However, any re-entrant/custom serializer or save-handler behavior capable of mutating/separating the progress array could stale these bucket pointers; investigate vendor patch for replacement with hash re-lookup. Preconditions: progress marker + SID + file, plus relevant callback/reentrancy. Detection value: crashes around these writes during multipart parsing; hardening value: disabling upload progress removes the writes.

Second hypothesis: event-state assumptions. FILE_DATA/FILE_END guard only SID+key, not `progress->data`, `current_file`, or cached pointers (`src/php-src-83/ext/session/session.c:3215-3244`). The stock parser normally emits FILE_START before these (`src/php-src-83/main/rfc1867.c:957-969,1005-1018,1076-1085`), but malformed/alternate callback chains are worth auditing. Historical regression coverage explicitly tests a malformed Content-Disposition that reaches END without a file start (`src/php-src-83/ext/session/tests/bug79221.phpt:23-47`); current END checks `progress->data` in the cleanup-disabled branch (`src/php-src-83/ext/session/session.c:3253-3259`). This supports event-state validation as a recurring bug class, though no current stock-parser violation was proven.

Ownership aliases `progress->files` and `current_file` are inserted into parents without clearing the source zval (`src/php-src-83/ext/session/session.c:3181,3207`). They function as non-owning aliases; only top-level `progress->data` is destroyed at END (`src/php-src-83/ext/session/session.c:3264-3265`). This is delicate but balanced in the observed path, not a demonstrated double-free.
